Apply this decision flow in order — stop at the first match for the primary layer.

1. Can a unit test cover the change in isolation? Pure logic, no live dependencies → UNIT
2. Does the change need real service wiring or real DB queries to verify? → INTEGRATION
3. Is this a full customer journey spanning multiple systems, requiring a real client, or a real authentication path? → BACKEND_E2E (API-driven) or PORTAL_UI_E2E (browser-driven)
4. Is the change purely frontend rendering or component state? → CYPRESS_COMPONENT (never PORTAL_UI_E2E for rendering bugs)
5. Does the change require real hardware, real third-party systems we cannot control, exploratory testing, or human judgment? → MANUAL

Test layers — always default to the lowest appropriate level:

- UNIT: pure logic, no live deps. Cheapest, fastest, most focused.
- INTEGRATION: real service wiring, real DB. Use WebApplicationFactory + Testcontainers (or your stack's equivalent). NEVER use SQLite for tests that seed or query data — the dialect drift bites you eventually.
- BACKEND_E2E: full API flows including real authentication and real backend services. More expensive than INTEGRATION; only use when the value is in the cross-service contract.
- PORTAL_UI_E2E: true end-to-end customer journeys through a real browser. NEVER use for rendering bugs or single-service API validation. Preconditions (users, groups, policies not under test) must be set up via API calls, not UI navigation.
- CYPRESS_COMPONENT: frontend rendering or component state in isolation. Fast, focused, and the right level for component bugs.
- MANUAL: real hardware, real third-party AD, exploratory testing, UX judgment, or non-deterministic concerns that cannot reliably be reproduced in CI.

Key rules:

- NEVER recommend PORTAL_UI_E2E for rendering bugs or single-service checks.
- If labelled BE_Only (backend only), do not consider PORTAL_UI_E2E.
- Always name the specific method, endpoint, or scenario to automate — don't just say "test the feature".
- Always include the repo path or test project where the test should live.
- Always state what still needs manual testing explicitly, even if the primary layer is automated.
- Unit tests are evaluated INDEPENDENTLY of the decision chain. Even when the primary layer is INTEGRATION or E2E, always ask: is there any business logic, validation rule, error handling, or guard method that can be tested in isolation with a mocked dependency? If yes, those are unit tests. The fact that a feature needs a real DB at integration level does NOT mean the underlying logic cannot be unit tested with mocks. Only skip unit tests for config-only changes, simple wiring with no logic, or pure pass-through methods. If skipping, state the reason explicitly.
